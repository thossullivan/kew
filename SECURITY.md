# Security Policy

kew runs autonomous coding agents against your repositories — it executes a coding model
with tool access, in a standalone clone of your repository, and opens pull requests. We
take the safety of that execution seriously, and security is a first-class part of the
product rather than an afterthought.

## Built-in safeguards

- **Official Codex native host sandbox.** The official Codex runner uses
  Codex-native `workspace-write` with command network off and protected `.git`.
  This differs from kew's external container mount boundary: kew records posture
  `native`, and the official CLI login remains host-managed.
  `workspace-write` restricts writes and network, not reads.
  Before every push, kew scans the added and changed files for the credential
  values it holds and for known key shapes, and refuses publication on a match.
  kew's host broker publishes through the canonical repository, the default
  `[publication] publish = "canonical"`. Its empty credential declaration makes mapped container
  execution fail closed in v1. The known-bypass and mount-boundary limits below
  remain unchanged.
- **Sandbox mount boundary (primary containment, deployment layer).** When
  containment is active, each dispatch runs inside an ephemeral container whose only
  volume mount is a standalone checkout of the issue branch — no host `~/.claude`,
  `dispatch.db`, or GitHub credentials are visible inside. This **mount boundary** is the
  primary containment mechanism: even a fully compromised agent cannot reach the audit
  database or any host secret other than its own runner's inference credential (the
  residual risk below), because nothing else is mounted or forwarded. Push and PR creation are
  host-brokered (kew runs `git push` and `gh pr create` on the host after the container
  exits). See [docs/configuration.md#sandbox](docs/configuration.md#sandbox) for the
  full option reference.
  Containment is active under the default `[sandbox] enabled = "auto"` when a
  container runtime is present, and under `enabled = true`.
  Without a runtime, both refuse a route that needs a container.
  Other than native Codex, a route runs on the host only with
  `[sandbox] dangerously_skip_containment = true`.

  **Residual risk — injected inference credential:** kew forwards the `ANTHROPIC_API_KEY`
  or `CLAUDE_CODE_OAUTH_TOKEN` into the container by environment variable so the agent can
  reach the Anthropic API. The default `[sandbox] network = "allowlist"` maps the container
  to a pre-configured Docker network named `kew-allowlist`; Docker refuses to start the
  container if that network does not exist (fail closed — no silent fallback to open
  egress). `kew sandbox network` creates that network as a plain bridge, which has
  unrestricted egress; kew installs no rules on it and records each run's egress as
  unverified. To restrict egress to Anthropic + GitHub only, create the network and add
  host-level iptables rules:
  ```
  docker network create --driver bridge kew-allowlist
  # then add iptables rules to allow only api.anthropic.com and github.com egress
  ```
  Setting `network = "open"` is the explicit opt-out to full egress (required if you have
  not configured the `kew-allowlist` network). With open egress a prompt-injected agent
  could exfiltrate the credential via outbound HTTP — operators who set `network = "open"`
  accept this residual risk.
- **Security hook (best-effort layer 2, Claude Code only).** Every Claude Code tool call
  passes through a security guard (`.claude/hooks/security-guard.sh`, generated by `kew setup`) that blocks
  attempts to read credentials, mutate git refs outside the assigned checkout, write to
  `.claude/`, or shell out in dangerous ways (subshells, `eval`, pipe-to-shell,
  base64-decode bypasses). It does not stop an agent reading or copying files outside
  the checkout (`cat ~/.ssh/id_rsa` passes); only the mount boundary does that. The
  `.claude/` Write/Edit block and the cross-checkout ref rule are keyed on a marker kew
  sets for dispatched agents on the host and, as `/work`, inside containers (#1691).
  **This guard is best-effort and known-bypassable in-process** — audit #502 identified
  eight bypass paths against the in-process guard alone. It remains a useful second layer
  in sandboxed mode (defence-in-depth) and the primary blocking control in host-subprocess
  mode (`[sandbox] enabled = false`), but do **not** rely on it as the sole containment
  boundary. [docs/security.md](docs/security.md) lists both the shapes it denies and the
  ones it deliberately does not model.
- **Standalone clone isolation.** Each agent works in a `--no-hardlinks` clone with its
  own `.git`, never a linked worktree of your repository and never directly on your main
  checkout — so the agent cannot write your `.git/config`, plant a hook that fires on your
  next commit, or share your object store.
- **Budgets + kill switch.** Per-issue, daily, and weekly spend caps, plus a fleet-wide
  `kew stop` that halts all in-flight runs.
- **Audit envelope.** Dispatch actions are recorded to a local, **hash-chained** audit
  trail (`kew audit tail` / `export`); `kew audit verify` checks integrity. The ledger
  host computes each anchor of the chain head and can push a copy off the host, so a
  later edit to anchored events is detectable — **tamper-evident
  within stated limits, not tamper-proof (kew is not an HSM).** See the
  [threat model](docs/threat-model.md) and [docs/audit.md](docs/audit.md) for the honest
  current guarantee and its exact ceilings.

For the full trust model — what kew defends against and, just as importantly, **what it
does not** (kew is a governance guardrail, not an OS sandbox) — see the
[threat model](docs/threat-model.md).

## Supply chain

- **Provenance attestations.** `kew-cli` is published to PyPI via OIDC Trusted
  Publishing with PEP 740 attestations — no long-lived tokens, and each release is
  cryptographically tied to the workflow that built it.
- **SBOM.** Every GitHub release carries a CycloneDX SBOM of the shipped (runtime)
  dependency tree (`kew-cli-<version>.sbom.cdx.json`).
- **License gate.** CI fails the build if any dependency carries a copyleft
  (GPL/LGPL/AGPL) license; the tree is otherwise permissive (MIT/Apache/BSD/PSF/ISC/MPL).
- **Continuous scanning.** Each push runs `pip-audit` (known CVEs), `bandit` + `semgrep`
  (SAST), and `gitleaks` (secret detection).

## Reporting a vulnerability

**Please do not open a public issue for security vulnerabilities.**

Report privately through GitHub's
[private vulnerability reporting](https://github.com/thossullivan/kew/security/advisories/new)
("Report a vulnerability" under the repository's **Security** tab). If that is unavailable,
email the maintainer at [tom@tomsullivan.dev](mailto:tom@tomsullivan.dev).

Please include:

- a description of the issue and its impact,
- steps to reproduce (a minimal `kew.toml` / command sequence is ideal),
- affected version (`kew --version`), and
- any suggested remediation.

We aim to acknowledge reports within 72 hours and to keep you updated as we work on a fix.
We'll credit reporters in the release notes unless you prefer to remain anonymous.

## Supported versions

kew ships from a single active line. Security fixes land on the latest
released version; please upgrade to the most recent release before reporting.

## Scope

Especially interested in: security-hook bypasses, checkout escapes, credential exposure
(env, logs, PR comments), prompt-injection via issue bodies or review comments, and
supply-chain concerns in the published `kew-cli` / `create-kew` packages.
